# 测试用例质量评审 Skill

## 激活场景
- 每批测试用例生成完成后（自动执行轻量自检）
- 用户要求"审查用例质量"或"评分"
- 用户要求生成测试质量报告
- 用例提交评审前的最终检查

---

## 评审模式选择（强制 — Phase 4 开始前执行）

根据项目规模选择评审模式：

```python
matrix = load_feature_matrix(project_identifier="...")
feature_count = len([f for f in matrix.get("features", []) if f.get("id", "").startswith("FP-")])
```

| 功能点数 | 模式 | 评审方式 | 说明 |
|---------|------|---------|------|
| ≤10 | 🚀 快速 | 仅覆盖率对照 + 交叉验证减分 | 不做完整四维度评分，不启动隔离 Agent |
| 11-30 | ⭐ 标准 | 四维度评分 + 交叉验证减分 + **隔离 Agent 评审** | 隔离 Agent 负责发现盲区问题 |
| >30 | 🏗️ 完整 | 四维度评分 + 交叉验证减分 + **隔离 Agent 评审** + 历史基线对比 | 最严格的质量门禁 |

> ⚡ **优先级规则**：用户或任务发起方**显式要求隔离评审/标准模式**时，优先于上表的规模判定（小规模项目也可启动隔离 Agent）；一旦启动，输出契约以 agent.py SYSTEM_PROMPT「Phase 4 隔离评审 task 契约」硬编码条款为准，禁止凭记忆改写。

## Phase 4 前置轻量预检（启动隔离 Agent 前必须执行）

在启动隔离 Agent 做对抗性评审之前，**先做一次覆盖度预检**以避免在覆盖率极低时浪费 token：

### 预检步骤
1. 读取 `feature_matrix.jsonl`，获取总功能点数 N
2. 扫描已生成的用例（通过 `preview_test_cases` 或逐模块 JSONL 文件），统计已覆盖的功能点数 C
3. 计算覆盖率 = C / N × 100%

### 路由决策
```
覆盖率 ≥ 80%  → 进入完整评审（启动隔离 Agent + 四维度评分）
覆盖率 50-80% → 仅做基础评审（四维度评分，跳过隔离 Agent）+ 标注 "⚠️ 覆盖率不足，未启动隔离评审"
覆盖率 < 50%  → 直接输出预检结果，建议回到 Phase 3 继续设计，不启动评审
```

### 覆盖率 < 80% 时的输出格式
```markdown
## ⚠️ Phase 4 前置预检

当前覆盖率：{C}/{N} = {pct}%
未覆盖功能点：{N-C} 个

| 未覆盖功能点 | 模块 | 优先级 | 风险 |
|-------------|------|--------|------|
| FP-XXX | ... | P0 | 高 |

⚠️ 覆盖率过低时深度评审收益有限，建议先回到 Phase 3 完成剩余模块的用例设计。

是否仍要进入完整评审？（回复「继续评审」或「回到 Phase 3」）
```

> ⚡ **目的**：避免在覆盖率仅 34.2% 时浪费 token 做注定失败的对抗性评审。
> 评审的价值与覆盖率成正比。

## 隔离 Agent 评审（标准/完整模式强制）

**原理**：AI 评审自己生成的用例存在天然盲区（确认偏误、一致性偏见）。引入一个独立的、带有 **"蓄意破坏者"思维** 的 Agent，专门寻找用例中的缺陷。

### 启动时机

在完成维度一~四的基础评分后，交叉验证减分之前。

### Agent 配置

使用 `task` 工具启动专用的 **`adversarial-reviewer`** 子代理（审查维度已内置在其系统提示中，任务消息只需提供事实信息）：

```python
task(
    subagent_type="adversarial-reviewer",
    description=f"""
请对以下测试用例集进行对抗性评审。

## 项目背景
{modules_summary}（模块清单、功能点范围、P0/高风险分布，3~8 行文本）

## 阶段约束摘要
{constraints_summary}（仅 test_types + 已确认假设，3~5 行文本，不贴完整 JSON）

## 审查输入（请自行 read_file 读取，大文件分段）
- 功能矩阵：{matrix_file_path}
- 用例文件清单：{case_file_paths}

## 结果目录
{会话工作目录}/（即运行时上下文注入的「会话工作目录」，形如 /<项目>/<会话ID>/；逐模块写入 adversarial_review_m{{NN}}.md，信任度评估写入 adversarial_review_summary.md）

审查重点分配：P0/高风险功能点的用例逐条审查；P2/P3 功能点抽样审查。
""",
)
```

> ⚡ **禁止再用 `general-purpose` 做隔离评审**：general-purpose 与主 Agent 共用
> max_tokens=8192 的模型，推理模型（deepseek-v4 系列）的 reasoning 与正文共享
> 该配额，逐条评审的思考链会耗尽配额导致返回空结果（finish_reason=length）。
> `adversarial-reviewer` 使用独立的大预算模型实例，并内置了 8 维度审查清单
> 与"逐模块写文件、最终只回摘要"的输出契约。

### Agent 结果整合

子代理最终消息只返回统计摘要（阻断数/附录数/信任度 + 文件清单）。收到摘要后按以下顺序整合：

1. **先调 `verify_review_citations` 做举证校验**（确定性 grep：阻断发现的「原文」引文必须能在本次用例 JSONL 中找到）。校验未证实的发现**不得进入阻断清单**——降级附录，并在评审报告中计数说明（幻觉举证信号）
2. 逐模块读取 `{会话工作目录}/adversarial_review_m*.md`：
   - 🚫 阻断发现（已证实）→ 评审报告「阻断清单」，逐条渲染（含原文引文与误判场景）
   - ⏳ 待确认假设 → 汇总进报告「待确认假设」清单（不算用例缺陷、不占修复义务，回流需求确认）
   - 📎 附录 → **不逐条渲染**，报告中只给各模块计数与文件指引（附录不阻塞放行，修复期可选处理）
3. 读取 `adversarial_review_summary.md`，信任度评估展示在评审报告的"补充建议"末尾
4. 交叉验证减分值需根据 Agent 发现的阻断问题**重新计算**（通常 Agent 会发现更多扣分项）
5. **结果文件缺失或为空时**：按模块拆分后重新发起 task（每次只审 1~2 个模块），禁止原样整体重试

> ⚡ **强制规则**：隔离 Agent 发现的阻断问题，**不得**在评审报告中为其辩解或弱化。Agent 说有问题就是有问题，除非你能用具体、可验证的证据推翻它。
> ⚡ **渲染减负铁律**：评审报告默认只渲染阻断清单 + 系统性缺口 + 待确认假设；附录全量保留在结果文件中供人工抽查，**禁止**把附录逐条搬进报告正文（会把核实成本转嫁给人）。

## 质量评审维度（Quality Dimensions）

### 维度一前置：结构化覆盖对照（强制）

在评估完整性之前，**必须先从磁盘读取 Phase 1 保存的结构化功能矩阵**，然后逐功能点对照已生成的用例，输出覆盖映射表。

**操作步骤：**

1. 读取功能矩阵文件，路径规则与 Phase 1 保存时保持一致（以保存工具返回的 `read_path` 为准，形如 `/<project_identifier>/<会话ID>/feature_matrix.jsonl`）：
   - 传入了 `project_identifier`：`<project_identifier>/<会话ID>/feature_matrix.jsonl`（即「会话工作目录」下）
   - 未传入 `project_identifier`：`feature_matrix.jsonl`
   - 后端代码可通过 `load_feature_matrix(project_identifier="...")` 获取同一文件
2. **从中提取 `constraints` 字段**（如果 Phase 1 已写入），获取：
   - `test_types`：用户限定的测试类型
   - `assumptions_confirmed`：阻塞性假设是否已确认
   - `blocking_assumptions`：待确认的假设列表
   - `user_feedback_summary`：用户各阶段反馈摘要
3. 调用 `compute_coverage_report(project_identifier=..., case_files=[本次 Phase 3 保存的全部模块 JSONL 文件])` 建立"功能点 → 用例"映射。**必须显式传 case_files**——不传时工具会扫描项目目录下全部 JSONL 文件（含历史会话遗留用例），覆盖率统计会被污染；若返回 warnings 提示扫描到非本次生成的文件，用本次模块文件清单重新调用
4. 输出覆盖率摘要（如 "22/25 个功能点已覆盖，覆盖率 88%"）
5. **输出约束一致性简报**（如存在 constraints）：
   ```
   ### 阶段约束一致性
   | 约束项 | Phase 1 设定 | 当前合规状态 |
   |--------|------------|------------|
   | 测试类型限定 | 仅 functional | ✅ 所有 46 条用例均为 functional 类型 |
   | 阻塞性假设确认 | 未确认 | ⚠️ 边界值数据仍基于默认假设 |
   ```

**若 feature_matrix.jsonl 不存在**（Phase 1 未调用 `save_feature_matrix_tool` 或 project_identifier 目录不匹配），在报告中明确标注：
> ⚠️ [无结构化矩阵] 覆盖度基于对话历史判断，可能存在遗漏。建议回退 Phase 1 重新生成功能矩阵。

**若 feature_matrix.jsonl 存在但无 `constraints` 字段**（Phase 1 未写入约束），在报告中标注：
> ⚠️ [无阶段约束] 无法验证用例是否与用户限定一致，请人工确认。

### 维度一：完整性检查（Completeness）- 权重30%

基于上一步的覆盖映射表，逐项验证覆盖情况：

```
✅ 检查项：
□ 所有功能点（Feature）均已设计对应测试用例
□ 每个功能点有正向用例（Happy Path）
□ 每个功能点有至少1个异常/负向用例
□ 关键业务流程的端到端场景已覆盖
□ 所有输入字段已考虑边界值
□ 所有P0功能点的已识别分支（正常/异常/边界）均有用例覆盖（条数不设下限）
□ 安全相关功能（认证/授权/输入验证）已有安全测试用例
□ 状态机转换的所有路径已覆盖

评分规则：
满足检查项数 / 总检查项数 × 100 = 完整性得分
```

### 维度二：准确性检查（Accuracy）- 权重25%

逐条用例检查预期结果的可验证性：

```
✅ 检查项（针对每条用例）：
□ 预期结果是否具体可验证（禁止"正确显示"、"正常"等模糊词）
□ 测试步骤是否清晰无歧义（每步只有一个操作）
□ 测试数据是否具体（有实际值而非"有效数据"等描述）
□ 前置条件是否可重现（避免依赖"上一步的结果"）
□ 用例是否真正只验证一个检查点（原子性）

❌ 红线词汇（出现即扣分）：
- "正确"、"成功"、"失败"（需改为具体状态描述）
- "合适"、"适当"、"美观"（主观描述）
- "等待"、"稍后"（时间不明确）
- "相关"、"对应"、"正常"（逻辑不明确）
```

### 维度三：有效性检查（Validity）- 权重25%

评估测试用例的实际执行价值：

```
✅ 检查项：
□ 每条用例是否能发现至少一类缺陷（不是形式用例）
□ 设计方法是否与测试场景匹配
□ 测试数据是否能有效触发目标逻辑
□ 是否存在重复用例（逻辑完全相同只换了一个数据）
□ 高优先级测试点是否使用了更严格的测试方法
□ 安全测试数据是否具备真实攻击价值

有效性分级：
高价值用例：能直接发现核心功能缺陷（计分×1.5）
标准用例：  验证正常逻辑（计分×1.0）
低效用例：  与其他用例重复或价值低（计分×0.5）
冗余用例：  完全重复，建议删除（计分×0）
```

### 维度四：可执行性检查（Executability）- 权重20%

确保用例可以被测试人员独立执行：

```
✅ 检查项：
□ 前置条件是否可独立准备（不依赖其他用例的执行结果）
□ 测试步骤是否足够详细（新人可独立执行）
□ 测试数据是否完整提供（不需要测试人员自己查找）
□ 预期结果是否可客观判定（有Pass/Fail标准）
□ 用例是否与环境紧密耦合（最好能在多环境执行）
□ 是否说明了所需的账号权限
```

### 维度五：交叉验证检查（Cross-Validation）- 减分项（防止"满分无问题"）

此为**减分维度**，不参与基础评分计算，但会在综合评分上进行扣分。目的是防止评审报告出现"100分零问题"的虚假合格。

```
🔍 强制交叉检查项（评审时必须逐项回答）：

□ 风险-分支覆盖匹配检查：
  标注为"高"风险的 P0 功能点，其全部已识别分支（正常/异常/边界/状态流转）是否各被至少 1 条用例覆盖？
  → 条数不设下限：分支全覆盖即达标，禁止为凑条数新增同规则用例（实测教训：凑密度新增的用例重复率高达 26%）
  → 分支存在明确缺口（如有"禁止/拦截"规则却无对应拦截用例）：扣 3 分并列入系统性缺口
  → 仅 1-2 条用例的 P0 功能点：须逐条说明分支覆盖完整性理由；说明不充分视同缺口，扣 3 分

□ 边界值假设依赖检查：
  边界值测试数据是否基于已确认的需求，还是来自 Phase 1 的默认假设？
  → 如存在"待确认依赖"，在报告中标注 ⚠️ 并扣 2 分（不列入问题清单但必须展示）

□ 跨用例数据一致性检查（抽样 3-5 条）：
  前置条件描述的字段/值与测试数据中的字段/值是否自洽？
  → 示例：前置条件说"默认显示 1"但测试数据是 {"port":"COM1"}，格式不一致应扣 2 分

□ 异常覆盖多样性检查：
  异常用例是否覆盖了以下维度？
  - 负值 / 零值 / 空值 / 超长值
  - 中文/Unicode/emoji/特殊字符（至少覆盖一类）
  - 格式错误（如数字字段传字母）
  → 缺少 ≥ 2 个维度，扣 2 分并列入系统性缺口

□ 阶段约束一致性检查（读取 feature_matrix.jsonl 的 constraints 字段）：
  用例的测试类型是否与用户限定的 test_types 一致？
  → 如用户限定"仅功能测试"但用例中存在安全测试类型，每个不一致用例扣 5 分并列入阻断清单
```

**减分汇总**：

| 检查项 | 扣分上限 | 触发条件 |
|--------|---------|---------|
| 风险-分支覆盖不匹配 | -3 分 | 高风险 P0 功能点已识别分支存在覆盖缺口，或仅 1-2 条用例且未给出分支覆盖完整性理由 |
| 边界值假设依赖 | -2 分 | 边界数据基于未确认的默认假设 |
| 跨用例数据不一致 | -2 分 | 前置条件与测试数据不自洽 |
| 异常覆盖维度不足 | -2 分 | 缺少 ≥ 2 个异常维度 |
| 阶段约束不一致 | -5 分/例 | 用例类型违背用户限定 |

> ⚡ **综合评分 = max(0, 基础评分 - 减分汇总)**。这意味着即使四个基础维度全部满分（100），交叉检查减分也可以将最终得分拉低到 85-90 分，迫使评审报告必须展示真实问题。

## 评审报告输出模板

```markdown
## 📊 测试用例质量评审报告

### 基本信息
| 项目 | 内容 |
|------|------|
| 评审模块 | [模块名称] |
| 用例总数 | [N] 条 |
| 评审时间 | [当前时间] |
| 评审版本 | v1.0 |

### 质量评分

| 维度 | 满分 | 得分 | 得分率 |
|------|------|------|--------|
| 完整性（Completeness） | 30 | [X] | [XX]% |
| 准确性（Accuracy） | 25 | [X] | [XX]% |
| 有效性（Validity） | 25 | [X] | [XX]% |
| 可执行性（Executability） | 20 | [X] | [XX]% |
| **基础评分** | **100** | **[X]** | **[XX]%** |
| 交叉验证减分 | — | [-X] | — |
| **综合评分** | — | **[X]** | **[XX]%** |

### 质量等级
```
90-100分：⭐⭐⭐⭐⭐ 企业级优秀水准，可直接用于回归测试库
75-89分： ⭐⭐⭐⭐   良好，修复问题项后可发布
60-74分： ⭐⭐⭐     合格，需要改进关键问题
60分以下： ⭐⭐      不合格，需要重新设计
```

> ⚠️ **评分自检规则**：由于交叉验证减分机制，满分（100分）应当是**极罕见的**。
> - 如果基础评分达到 100 但交叉验证未逐项执行，**必须退回重新评审**
> - 如果交叉验证发现 ≥ 2 项应扣分但评审报告未体现，评审无效
> - 当所有边界值数据基于未确认的默认假设时，综合评分不应超过 95 分

### 覆盖度分析

| 功能模块 | 需求功能点数 | 已覆盖用例数 | 覆盖率 | 缺口说明 |
|---------|-----------|-----------|--------|---------|
| [模块A] | [N] | [N] | [N]% | [缺失的功能点] |
| [模块B] | [N] | [N] | [N]% | [无/说明] |
| **汇总** | [N] | [N] | [N]% | - |

### 阻断清单（必须修复 — 隔离评审已证实发现）

> 每条均通过 `verify_review_citations` 举证校验。未证实发现已降级附录（计数见附录节）。

| 用例编号 | 位置 | 问题 | 原文证据 | 误判场景 | 修复建议 |
|---------|------|------|---------|---------|---------|
| TC-XXX-001 | 步骤 2 预期 | 断言与需求冲突 | "…逐字引文…" | 执行时 … → 误报 | 改为"HTTP 200，响应体包含user_id字段" |

### 🔍 冗余审查（强制 — 无冗余也必须显式声明）

逐功能点对照全部用例的 test_point 与步骤结构，识别三类冗余：**子集**（A 的场景完全被 B 包含）、**同规则**（验证同一业务规则、仅数据不同）、**同构**（步骤结构相同、仅操作对象不同）。

| 疑似冗余对 | 重复类型 | 处理建议 |
|-----------|---------|---------|
| TC-XXX ↔ TC-YYY | 子集/同规则/同构 | 删除 TC-XXX，其独有断言并入 TC-YYY |

确认冗余的用例按上表列出，并在有效性维度按"冗余用例计分×0"扣分。**无冗余时必须输出一行结论**：「本次评审已对照全部用例的 test_point 与步骤结构，未发现冗余」——禁止省略本小节。

### ⚠️ 系统性缺口（分支覆盖/维度/覆盖类，非单条用例缺陷）

| 缺口 | 涉及功能点 | 说明 | 补救建议 |
|------|-----------|------|---------|
| P0 分支覆盖缺口 | FP-013 | "部分失败"分支无用例（现有 2 条均为正常流） | 补部分失败+回滚场景 |

### ⏳ 待确认假设（回流需求确认，不算修复义务）

| 假设 | 涉及用例 | 当前默认 | 影响 |
|------|---------|---------|------|
| 备注 40 字符计数规则 | TASK-002 | 按字符计，超长禁止输入 | 约 3 条边界用例 |

### 📎 附录（N 条，不阻塞放行）

各模块分布：m01: N / m02: N / …（含隔离评审附录 N 条 + 举证未证实降级 N 条）。
详见 `adversarial_review_m*.md`。修复阻断项时可顺带处理；放行后建议抽样核查。
```

## 补充建议填充规则（强制 — 禁止空表头）

「补充建议」小节**禁止只输出表头**（系统会检测空表并退回报告）。每条建议必须来自以下确定性来源之一，不允许凭空编造，也不允许留空：

| 来源 | 转化规则 | 建议类型示例 |
|------|---------|------------|
| `compute_coverage_report` 返回的未覆盖/疑似覆盖功能点 | 每个 ❌ 未覆盖功能点 → 1 行新增用例建议 | 覆盖补全 |
| 对抗性评审阻断清单 / 附录（`adversarial_review_m*.md`） | 涉及"缺少某类用例"的发现 → 1 行建议 | 安全测试 / 异常测试 / 边界测试 |
| 交叉验证缺口（维度五） | 异常覆盖维度不足、风险-分支覆盖不匹配 → 1 行建议 | 异常测试 / 分支覆盖补强 |

**写法要求**：

1. 「描述」列必须引用具体 FP-ID 或用例编号（如 `FP-012 部分退款未覆盖，建议补充部分退款+余额混合支付场景`），禁止"建议加强测试""建议完善覆盖"等空泛描述
2. **以上来源确实均无内容可填时**：将表格写为一行 `| 无 | 本次评审未发现需要新增的用例方向 | - |`，或直接删除整个「补充建议」小节——二选一，**禁止保留只有表头的空表**
3. 「测试风险提示」同理：无风险时写 `- ⚠️ 无` 或删除该小节，禁止只留标题

## 评审回退机制（Remediation Workflow）

当质量评审综合评分低于 75 分时，必须执行回退修复流程。

### 回退判定标准

| 评分区间 | 判定 | 回退动作 |
|---------|------|---------|
| 90-100 | 优秀 | 直接通过，可发布 |
| 75-89 | 良好 | 修复问题项后通过 |
| 60-74 | 合格 | **必须回退**：修复关键问题后重新评审 |
| <60 | 不合格 | **必须回退**：重新设计后重新评审 |

### 回退时的 AI 强制阻断措辞

当评审评分 < 75 时，AI **必须**输出以下阻断语，**不得**直接标志 Phase 4 为 completed：

| 评分区间 | AI 必须输出的阻断语 |
|---------|-------------------|
| 60-74 | "⚠️ 评审未达标（{score} 分）。以下 N 个问题必须修复后重新评审。若要跳过返工，请回复「确认跳过返工」（风险自负）。" |
| <60 | "❌ 评审不合格（{score} 分）。覆盖率仅 {coverage}%，{N} 个 P0 功能点无用例。强烈建议回到 Phase 3 完成剩余模块。若仍要跳过返工，请回复「确认跳过返工」。" |

> ⚡ **关键变更**：评审不达标时，AI **不得**在用户回复"报告已确认，请继续"后就推进到 Phase 5。
> 用户必须明确回复 **「确认跳过返工」**（完整匹配）才能放行。
> 另外，综合评分 < 75 时中间件会自动退回最多 2 轮，AI 应配合返工。

### 回退修复流程（增量式 — 强制）

```
Step 1: 问题分级
  ├─ 读取评审报告中的阻断清单 / 系统性缺口 / 待确认假设
  ├─ 阻断清单 = 必须修复；系统性缺口 = 本轮修复
  ├─ 待确认假设 = 回流需求确认（不算用例缺陷）
  └─ 附录 = 按类型分流：
      ├─ 冗余类（同规则/子集/同构）= 必须逐条处置（删除/合并/声明保留理由）
      └─ 其余（措辞/编号规范/数据丰富度）= 可选处理（不纳入修复率统计）

Step 2: 修复优先级排序
  修复顺序：
  1. 阻断清单（必误报/必漏报/不可执行）
  2. 系统性缺口（P0 分支覆盖缺口、异常维度不足、覆盖缺口）
  3. 冗余类附录（结构性缺陷：同规则/子集/同构——必须逐条处置，禁止无视）
  4. 其余附录（编号规范、措辞、数据丰富度——可选）

Step 3: 修复执行
  ├─ 阻断清单：必须全部修复
  ├─ 系统性缺口：修复率 ≥ 80%
  ├─ 待确认假设：汇总一次性向用户确认，按确认结果改受影响用例
  ├─ 冗余类附录：逐条给出处置结论并写入修复记录（三选一：删除 / 合并 / 保留+理由）
  └─ 其余附录：选择性采纳（不阻塞放行）

Step 4: 重新评审（增量式）
  ├─ 只复核本轮修改涉及的用例与功能点，不重新全量评审
  ├─ 第 2 轮起重评跳过隔离 Agent（首轮已暴露系统性问题，重复启动收益低）
  ├─ 评分依据：代码门禁校验 + compute_coverage_report + 本轮修复核对
  └─ 若仍低于75分，重复 Step 1-3（最多2轮，与系统自动退回轮次对齐）

Step 5: 最终判定
  ├─ 评分 ≥ 75：通过，输出最终评审报告
  └─ 2轮后仍 < 75：转人工评审卡片，由用户决定继续返工或跳过

Step 6: 重评报告输出要求（系统判定依据）
  └─ 评分表若包含历史版本对比列（v1/v2 得分），必须在报告末尾单独一行
     输出最终结论「综合评分：N 分」——系统以文末结论行为准，
     对比表中的历史分数列不作为判定依据
```

> ⚡ **增量修复铁律（防止返工时 token 爆炸）**：
> 1. **禁止重读全部用例文件** —— 按问题清单中的用例编号，用 `edit_file` 定点修改对应行
> 2. **禁止全量重写 JSONL 文件** —— write_file 重建整个文件会让全部用例再序列化一遍
> 3. **新增用例写入独立的 supplement 文件**（如 `test_cases_supplement.jsonl`），不动原有文件
> 4. **同一文件的多个修改，每轮消息只编辑一处**（并行 edit 同一文件只有最后一个生效）
> 5. **返工阶段不入库**：本批用例在 Phase 4 通过后才统一入库（`batch_create_test_cases_tool(input_file=[...])`），
>    返工修复只改 JSONL 文件即可，**禁止**在返工时调用任何入库工具；
>    `batch_update_test_cases_tool` 仅用于修改历史会话中已入库的用例
> 6. **新增用例必须附必要性声明** —— 每条 supplement 用例在修复记录中声明：该场景未被任何既有用例覆盖的理由，并引用最接近的既有用例编号对比（如"与 TC-CFG-003 的差异：其验证导入文件损坏，本条验证 GBK 编码异常"）。写不出明确差异的用例**禁止新增**——返工为凑密度而生的用例是冗余的主要来源（实测重复率 26%，远高于初始生成的 2%）。
> 7. **冗余类附录的处置操作要求** —— 删除冗余用例用 `edit_file` 定点删除对应 JSONL 行（编号空洞不重排，避免连锁改动）；合并时把被删用例的**独有断言点/测试数据**并入保留用例，修复记录写明「X 并入 Y：独有点 Z」；声明保留的冗余对必须给出两侧断言不互相覆盖的具体差异（不接受"侧重点不同"这类空话）。处置后核对：被删用例所属功能点仍有 ≥1 条用例覆盖。

## 历史质量基线对比

企业级质量评审不仅要评估当前用例的绝对质量，还要与历史基线进行相对比较。

### 基线数据来源

`rag-query` Skill 检索到的历史测试数据可作为质量基线：

| 基线类型 | 来源 | 用途 |
|---------|------|------|
| 历史覆盖率 | 同模块历史用例的功能覆盖范围 | 对比当前是否达到或超越历史水平 |
| 历史优先级分布 | 同模块历史用例的 P0/P1/P2/P3 比例 | 对比当前优先级分配是否合理 |
| 历史缺陷密度 | 该模块的历史 Bug 数量 / 用例数 | 高风险模块应投入更多测试资源 |
| 历史评审评分 | 同模块历史用例的评审得分 | 对比当前质量趋势（提升/下降）|

### 基线对比报告模板

```markdown
### 质量基线对比

| 指标 | 历史基线 | 当前值 | 差异 | 趋势 |
|------|---------|--------|------|------|
| 功能覆盖率 | 85% | 92% | +7% | ↑ 提升 |
| P0用例数 | 3条 | 5条 | +2条 | ↑ 提升 |
| 安全用例数 | 0条 | 2条 | +2条 | ↑ 提升 |
| 综合评分 | 78分 | 82分 | +4分 | ↑ 提升 |
| 边界值覆盖率 | 60% | 75% | +15% | ↑ 提升 |

**趋势分析**：[当前质量较历史基线有提升，但边界值覆盖率仍有提升空间]
```

## 问题分级与修复优先级

### 问题分级标准

| 级别 | 标识 | 定义 | 报告归组 | 修复时限 | 影响发布 |
|------|------|------|---------|---------|---------|
| **严重** | 🔴 | 导致用例不可执行、预期结果无法判定、存在重大安全遗漏 | 🚫 阻断清单 | 立即修复 | 阻塞 |
| **一般** | 🟡 | 覆盖率不足、边界值遗漏、数据不完整、优先级分配不合理 | ⚠️ 系统性缺口 | 本轮修复 | 需审批 |
| **优化** | 🔵 | 编号不规范、步骤可精简、数据可更丰富、格式不统一 | 📎 附录 | 下轮迭代 | 不阻塞 |

### 阻断级问题清单（必须立即修复 — 对应报告的🚫阻断清单）

```
□ 用例预期结果使用模糊描述（"正确""成功""正常"等）
□ 用例缺少具体测试数据（使用"有效数据"等描述性占位）
□ 前置条件依赖其他用例执行结果
□ 核心功能点（P0相关）无任何用例覆盖

□ 用例编号重复或格式错误

□ 一个用例验证多个不相关检查点（违反原子性）
```

## 自检触发规则（轻量版）

每次生成完一个模块的用例后，自动执行快速自检。

> ⚡ **代码门禁已覆盖的检查项禁止再用 LLM 逐条检查**：编号重复/格式、模块一致性、
> test_data 空对象、P0 数量、模块编号前缀、模糊预期结果（"正确/成功/正常"）——
> 这些由 CaseQualityGate / ModuleSelfCheck 中间件在创建前确定性校验，
> 重复检查纯属浪费 token。

```
LLM 快速自检项（4 项，仅代码判不了的）：
1. □ 模块所有功能点都有对应用例（对照 feature_matrix.jsonl）
2. □ 包含至少 1 条安全相关用例（条件性：Phase 1 constraints 排除安全测试时跳过）
3. □ 包含至少 1 条异常场景用例
4. □ 每条用例只验证一个独立检查点（原子性）

全部通过 → 输出"✅ 自检通过"
任一不通过 → 补齐后继续，无需长篇输出
```
