# 测试用例质量评审 Skill

## 激活场景
- 每批测试用例生成完成后（自动执行轻量自检）
- 用户要求"审查用例质量"或"评分"
- 用户要求生成测试质量报告
- 用例提交评审前的最终检查

---

## 评审模式选择（强制 — Phase 4 开始前执行）

根据项目规模选择评审模式：

```python
matrix = load_feature_matrix(project_identifier="...")
feature_count = len([f for f in matrix.get("features", []) if f.get("id", "").startswith("FP-")])
```

| 功能点数 | 模式 | 评审方式 | 说明 |
|---------|------|---------|------|
| ≤10 | 🚀 快速 | 仅覆盖率对照 + 交叉验证减分 | 不做完整四维度评分，不启动隔离 Agent |
| 11-30 | ⭐ 标准 | 四维度评分 + 交叉验证减分 + **隔离 Agent 评审** | 隔离 Agent 负责发现盲区问题 |
| >30 | 🏗️ 完整 | 四维度评分 + 交叉验证减分 + **隔离 Agent 评审** + 历史基线对比 | 最严格的质量门禁 |

## Phase 4 前置轻量预检（启动隔离 Agent 前必须执行）

在启动隔离 Agent 做对抗性评审之前，**先做一次覆盖度预检**以避免在覆盖率极低时浪费 token：

### 预检步骤
1. 读取 `feature_matrix.jsonl`，获取总功能点数 N
2. 扫描已生成的用例（通过 `preview_test_cases` 或逐模块 JSONL 文件），统计已覆盖的功能点数 C
3. 计算覆盖率 = C / N × 100%

### 路由决策
```
覆盖率 ≥ 80%  → 进入完整评审（启动隔离 Agent + 四维度评分）
覆盖率 50-80% → 仅做基础评审（四维度评分，跳过隔离 Agent）+ 标注 "⚠️ 覆盖率不足，未启动隔离评审"
覆盖率 < 50%  → 直接输出预检结果，建议回到 Phase 3 继续设计，不启动评审
```

### 覆盖率 < 80% 时的输出格式
```markdown
## ⚠️ Phase 4 前置预检

当前覆盖率：{C}/{N} = {pct}%
未覆盖功能点：{N-C} 个

| 未覆盖功能点 | 模块 | 优先级 | 风险 |
|-------------|------|--------|------|
| FP-XXX | ... | P0 | 高 |

⚠️ 覆盖率过低时深度评审收益有限，建议先回到 Phase 3 完成剩余模块的用例设计。

是否仍要进入完整评审？（回复「继续评审」或「回到 Phase 3」）
```

> ⚡ **目的**：避免在覆盖率仅 34.2% 时浪费 token 做注定失败的对抗性评审。
> 评审的价值与覆盖率成正比。

## 隔离 Agent 评审（标准/完整模式强制）

**原理**：AI 评审自己生成的用例存在天然盲区（确认偏误、一致性偏见）。引入一个独立的、带有 **"蓄意破坏者"思维** 的 Agent，专门寻找用例中的缺陷。

### 启动时机

在完成维度一~四的基础评分后，交叉验证减分之前。

### Agent 配置

```python
# 使用 Agent 工具启动一个独立的评审 Agent
Agent(
    subagent_type="general-purpose",  # 或专用的 "adversarial-reviewer" 类型
    description="对测试用例进行对抗性评审",
    prompt=f"""
你是一个**对抗性评审专家**。你的唯一目标是**找出测试用例集中的缺陷**。

不要寻找"做得好的地方"，不要做任何正面评价。你只输出问题和风险。

请从以下角度逐条审查用例：

1. **逻辑矛盾**：前置条件与测试数据是否自洽？步骤顺序是否合理？预期结果与操作是否有因果断裂？
   - 示例错误：前置条件说"默认显示 1"但测试数据是 {{"port": "COM1"}}，格式不一致

2. **覆盖盲区**：检查功能矩阵中的每个 test_point 是否至少被一条用例覆盖？是否存在"标注高-risk 但用例密度不足 6 条"的功能点？
   - 示例错误：FP-001 标注风险=高，但只有 6 条用例（建议 ≥ 8 条）

3. **假设依赖风险**：所有边界值数据是否来自已确认的需求？如果来自 Phase 1 的默认假设，标注这些用例是"待确认依赖"。
   - 示例错误：18 条边界值用例基于"范围 0~9999.99"的假设，但该假设从未被用户逐条确认

4. **异常覆盖单调**：异常输入是否覆盖了足够的多样性？检查是否有以下维度的缺失：
   - 负值、零值、空值、超长值、格式错误、Unicode/emoji、中文字符

5. **冗余检测**：是否存在逻辑完全相同只是换了一个测试数据的用例对？标出可以被合并的用例。

6. **可执行性缺陷**：是否所有前置条件都可以独立准备？测试数据是否完整？步骤是否新人可执行？

审查范围：
- 功能矩阵：{json.dumps(features, ensure_ascii=False)}
- 约束条件：{json.dumps(constraints, ensure_ascii=False)}
- 测试用例：{test_cases_summary}

请按以下格式输出：
## 🔍 对抗性审查发现

### 🔴 严重缺陷（N 个）
| # | 涉及用例 | 缺陷类型 | 详细描述 |
|---|---------|---------|---------|

### 🟡 可改进项（N 个）
| # | 涉及用例 | 改进方向 | 详细描述 |
|---|---------|---------|---------|

### 📊 信任度评估
- 整体可信度：[高/中/低]
- 最不可信的区域：[功能点/模块名]
- 理由：[一句话]
"""
)
```

### Agent 结果整合

隔离 Agent 返回的结果**必须**原样纳入评审报告：

1. Agent 发现的 🔴 严重缺陷直接进入评审报告的问题清单（严重问题）
2. Agent 发现的 🟡 可改进项直接进入评审报告的问题清单（一般问题）
3. Agent 的信任度评估展示在评审报告的"补充建议"末尾
4. 交叉验证减分值需根据 Agent 发现的问题**重新计算**（通常 Agent 会发现更多扣分项）

> ⚡ **强制规则**：隔离 Agent 发现问题后，**不得**在评审报告中为其辩解或弱化。Agent 说有问题就是有问题，除非你能用具体、可验证的证据推翻它。

## 质量评审维度（Quality Dimensions）

### 维度一前置：结构化覆盖对照（强制）

在评估完整性之前，**必须先从磁盘读取 Phase 1 保存的结构化功能矩阵**，然后逐功能点对照已生成的用例，输出覆盖映射表。

**操作步骤：**

1. 读取功能矩阵文件，路径规则与 Phase 1 保存时保持一致：
   - 传入了 `project_identifier`：`<project_identifier>/feature_matrix.jsonl`
   - 未传入 `project_identifier`：`feature_matrix.jsonl`
   - 后端代码可通过 `load_feature_matrix(project_identifier="...")` 获取同一文件
2. **从中提取 `constraints` 字段**（如果 Phase 1 已写入），获取：
   - `test_types`：用户限定的测试类型
   - `assumptions_confirmed`：阻塞性假设是否已确认
   - `blocking_assumptions`：待确认的假设列表
   - `user_feedback_summary`：用户各阶段反馈摘要
3. 扫描所有用例 JSONL 文件（或用 `preview_test_cases` 抽样各模块），建立"功能点 → 用例"映射
4. 输出覆盖率摘要（如 "22/25 个功能点已覆盖，覆盖率 88%"）
5. **输出约束一致性简报**（如存在 constraints）：
   ```
   ### 阶段约束一致性
   | 约束项 | Phase 1 设定 | 当前合规状态 |
   |--------|------------|------------|
   | 测试类型限定 | 仅 functional | ✅ 所有 46 条用例均为 functional 类型 |
   | 阻塞性假设确认 | 未确认 | ⚠️ 边界值数据仍基于默认假设 |
   ```

**若 feature_matrix.jsonl 不存在**（Phase 1 未调用 `save_feature_matrix_tool` 或 project_identifier 目录不匹配），在报告中明确标注：
> ⚠️ [无结构化矩阵] 覆盖度基于对话历史判断，可能存在遗漏。建议回退 Phase 1 重新生成功能矩阵。

**若 feature_matrix.jsonl 存在但无 `constraints` 字段**（Phase 1 未写入约束），在报告中标注：
> ⚠️ [无阶段约束] 无法验证用例是否与用户限定一致，请人工确认。

### 维度一：完整性检查（Completeness）- 权重30%

基于上一步的覆盖映射表，逐项验证覆盖情况：

```
✅ 检查项：
□ 所有功能点（Feature）均已设计对应测试用例
□ 每个功能点有正向用例（Happy Path）
□ 每个功能点有至少1个异常/负向用例
□ 关键业务流程的端到端场景已覆盖
□ 所有输入字段已考虑边界值
□ 所有P0功能点用例数量 ≥ 3个
□ 安全相关功能（认证/授权/输入验证）已有安全测试用例
□ 状态机转换的所有路径已覆盖

评分规则：
满足检查项数 / 总检查项数 × 100 = 完整性得分
```

### 维度二：准确性检查（Accuracy）- 权重25%

逐条用例检查预期结果的可验证性：

```
✅ 检查项（针对每条用例）：
□ 预期结果是否具体可验证（禁止"正确显示"、"正常"等模糊词）
□ 测试步骤是否清晰无歧义（每步只有一个操作）
□ 测试数据是否具体（有实际值而非"有效数据"等描述）
□ 前置条件是否可重现（避免依赖"上一步的结果"）
□ 用例是否真正只验证一个检查点（原子性）

❌ 红线词汇（出现即扣分）：
- "正确"、"成功"、"失败"（需改为具体状态描述）
- "合适"、"适当"、"美观"（主观描述）
- "等待"、"稍后"（时间不明确）
- "相关"、"对应"、"正常"（逻辑不明确）
```

### 维度三：有效性检查（Validity）- 权重25%

评估测试用例的实际执行价值：

```
✅ 检查项：
□ 每条用例是否能发现至少一类缺陷（不是形式用例）
□ 设计方法是否与测试场景匹配
□ 测试数据是否能有效触发目标逻辑
□ 是否存在重复用例（逻辑完全相同只换了一个数据）
□ 高优先级测试点是否使用了更严格的测试方法
□ 安全测试数据是否具备真实攻击价值

有效性分级：
高价值用例：能直接发现核心功能缺陷（计分×1.5）
标准用例：  验证正常逻辑（计分×1.0）
低效用例：  与其他用例重复或价值低（计分×0.5）
冗余用例：  完全重复，建议删除（计分×0）
```

### 维度四：可执行性检查（Executability）- 权重20%

确保用例可以被测试人员独立执行：

```
✅ 检查项：
□ 前置条件是否可独立准备（不依赖其他用例的执行结果）
□ 测试步骤是否足够详细（新人可独立执行）
□ 测试数据是否完整提供（不需要测试人员自己查找）
□ 预期结果是否可客观判定（有Pass/Fail标准）
□ 用例是否与环境紧密耦合（最好能在多环境执行）
□ 是否说明了所需的账号权限
```

### 维度五：交叉验证检查（Cross-Validation）- 减分项（防止"满分无问题"）

此为**减分维度**，不参与基础评分计算，但会在综合评分上进行扣分。目的是防止评审报告出现"100分零问题"的虚假合格。

```
🔍 强制交叉检查项（评审时必须逐项回答）：

□ 风险-密度匹配检查：
  标注为"高"风险的功能点是否有 ≥ 6 条用例？
  → 如有高风险的 P0 功能点仅有 3-5 条用例，扣 3 分并列入 🟡 一般问题

□ 边界值假设依赖检查：
  边界值测试数据是否基于已确认的需求，还是来自 Phase 1 的默认假设？
  → 如存在"待确认依赖"，在报告中标注 ⚠️ 并扣 2 分（不列入问题清单但必须展示）

□ 跨用例数据一致性检查（抽样 3-5 条）：
  前置条件描述的字段/值与测试数据中的字段/值是否自洽？
  → 示例：前置条件说"默认显示 1"但测试数据是 {"port":"COM1"}，格式不一致应扣 2 分

□ 异常覆盖多样性检查：
  异常用例是否覆盖了以下维度？
  - 负值 / 零值 / 空值 / 超长值
  - 中文/Unicode/emoji/特殊字符（至少覆盖一类）
  - 格式错误（如数字字段传字母）
  → 缺少 ≥ 2 个维度，扣 2 分并列入 🔵 优化建议

□ 阶段约束一致性检查（读取 feature_matrix.jsonl 的 constraints 字段）：
  用例的测试类型是否与用户限定的 test_types 一致？
  → 如用户限定"仅功能测试"但用例中存在安全测试类型，每个不一致用例扣 5 分并列入 🔴 严重问题
```

**减分汇总**：

| 检查项 | 扣分上限 | 触发条件 |
|--------|---------|---------|
| 风险-密度不匹配 | -3 分 | 高/中风险功能点用例密度不足 |
| 边界值假设依赖 | -2 分 | 边界数据基于未确认的默认假设 |
| 跨用例数据不一致 | -2 分 | 前置条件与测试数据不自洽 |
| 异常覆盖维度不足 | -2 分 | 缺少 ≥ 2 个异常维度 |
| 阶段约束不一致 | -5 分/例 | 用例类型违背用户限定 |

> ⚡ **综合评分 = max(0, 基础评分 - 减分汇总)**。这意味着即使四个基础维度全部满分（100），交叉检查减分也可以将最终得分拉低到 85-90 分，迫使评审报告必须展示真实问题。

## 评审回退机制（Remediation Workflow）

当质量评审综合评分低于 75 分时，必须执行回退修复流程。

### 回退判定标准

| 评分区间 | 判定 | 回退动作 |
|---------|------|---------|
| 90-100 | 优秀 | 直接通过，可发布 |
| 75-89 | 良好 | 修复问题项后通过 |
| 60-74 | 合格 | **必须回退**：修复关键问题后重新评审 |
| <60 | 不合格 | **必须回退**：重新设计后重新评审 |

### 回退时的 AI 强制阻断措辞

当评审评分 < 75 时，AI **必须**输出以下阻断语，**不得**直接标志 Phase 4 为 completed：

| 评分区间 | AI 必须输出的阻断语 |
|---------|-------------------|
| 60-74 | "⚠️ 评审未达标（{score} 分）。以下 N 个问题必须修复后重新评审。若要跳过返工，请回复「确认跳过返工」（风险自负）。" |
| <60 | "❌ 评审不合格（{score} 分）。覆盖率仅 {coverage}%，{N} 个 P0 功能点无用例。强烈建议回到 Phase 3 完成剩余模块。若仍要跳过返工，请回复「确认跳过返工」。" |

> ⚡ **关键变更**：评审不达标时，AI **不得**在用户回复"报告已确认，请继续"后就推进到 Phase 5。
> 用户必须明确回复 **「确认跳过返工」**（完整匹配）才能放行。
> 另外，综合评分 < 75 时中间件会自动退回最多 2 轮，AI 应配合返工。

### 回退修复流程

```
Step 1: 问题分级
  ├─ 读取评审报告中的问题清单
  ├─ 按严重程度标记：严重(🔴) / 一般(🟡) / 优化(🔵)
  └─ 统计各级问题数量

Step 2: 修复优先级排序
  修复顺序：
  1. 严重问题（预期结果模糊、缺少测试数据、用例不可执行）
  2. 一般问题（覆盖率不足、边界值遗漏、安全用例缺失）
  3. 优化建议（用例编号规范、步骤精简、数据丰富度）

Step 3: 修复执行
  ├─ 严重问题：必须全部修复
  ├─ 一般问题：修复率 ≥ 80%
  └─ 优化建议：选择性采纳

Step 4: 重新评审
  ├─ 修复完成后，重新执行 quality-review
  ├─ 对比修复前后的评分变化
  └─ 若仍低于75分，重复 Step 1-3（最多3轮）

Step 5: 最终判定
  ├─ 评分 ≥ 75：通过，输出最终评审报告
  └─ 3轮后仍 < 75：输出「⚠️ 质量风险警告」，说明已尽力修复但未达标，需人工介入决策
```

## 历史质量基线对比

企业级质量评审不仅要评估当前用例的绝对质量，还要与历史基线进行相对比较。

### 基线数据来源

`rag-query` Skill 检索到的历史测试数据可作为质量基线：

| 基线类型 | 来源 | 用途 |
|---------|------|------|
| 历史覆盖率 | 同模块历史用例的功能覆盖范围 | 对比当前是否达到或超越历史水平 |
| 历史优先级分布 | 同模块历史用例的 P0/P1/P2/P3 比例 | 对比当前优先级分配是否合理 |
| 历史缺陷密度 | 该模块的历史 Bug 数量 / 用例数 | 高风险模块应投入更多测试资源 |
| 历史评审评分 | 同模块历史用例的评审得分 | 对比当前质量趋势（提升/下降）|

### 基线对比报告模板

```markdown
### 质量基线对比

| 指标 | 历史基线 | 当前值 | 差异 | 趋势 |
|------|---------|--------|------|------|
| 功能覆盖率 | 85% | 92% | +7% | ↑ 提升 |
| P0用例数 | 3条 | 5条 | +2条 | ↑ 提升 |
| 安全用例数 | 0条 | 2条 | +2条 | ↑ 提升 |
| 综合评分 | 78分 | 82分 | +4分 | ↑ 提升 |
```

## 问题分级与修复优先级

### 问题分级标准

| 级别 | 标识 | 定义 | 修复时限 | 影响发布 |
|------|------|------|---------|---------|
| **严重** | 🔴 | 导致用例不可执行、预期结果无法判定、存在重大安全遗漏 | 立即修复 | 阻塞 |
| **一般** | 🟡 | 覆盖率不足、边界值遗漏、数据不完整、优先级分配不合理 | 本轮修复 | 需审批 |
| **优化** | 🔵 | 编号不规范、步骤可精简、数据可更丰富、格式不统一 | 下轮迭代 | 不阻塞 |

### 严重问题清单（必须立即修复）

```
□ 用例预期结果使用模糊描述（"正确""成功""正常"等）
□ 用例缺少具体测试数据（使用"有效数据"等描述性占位）
□ 前置条件依赖其他用例执行结果
□ 核心功能点（P0相关）无任何用例覆盖
□ 涉及用户输入的功能点无任何安全测试用例
□ 用例编号重复或格式错误
□ 测试步骤包含无法量化的描述（"等待片刻""稍后"）
□ 一个用例验证多个不相关检查点（违反原子性）
```

## 自检触发规则（轻量版）

每次生成完一个模块的用例后，自动执行快速自检：

```
快速自检项（13项）：
1.  □ 模块所有功能点都有对应用例
2.  □ 无一条用例使用模糊预期结果
3.  □ 每个用例都有具体测试数据（禁止 {} 空对象）
4.  □ P0用例数量合理（至少3条）
5.  □ 包含至少1条安全相关用例（条件性：仅当 Phase 1 constraints 未排除安全测试时检查；若用户限定"仅功能测试"则跳过此项）
6.  □ 包含至少1条异常场景用例
7.  □ 用例编号无重复
8.  □ 前置条件均可独立准备
9.  □ 测试步骤步数合理（5-15步）
10. □ 预期结果包含UI、数据两个层面验证
11. □ 每条用例只验证一个独立检查点（原子性：一条用例内的 test_case_steps 不应包含 ≥2 个可独立拆分的 Pass/Fail 判定）
12. □ 无 test_data 为空对象 {} 的用例（纯 UI 操作用例须填上下文描述字段，如 {"当前页码": 1}）
13. □ 所属模块的编号前缀与预分配表一致

通过12-13项 → 输出"✅ 自检通过"
通过10-11项 → 输出"⚠️ 自检发现小问题"并列出
通过<10项   → 输出"❌ 需要重新设计"并列出所有问题
```
