# 需求深度解析 Skill

## 激活场景
- 用户上传或粘贴需求文档（PDF、Word、Markdown、纯文本）
- 用户描述产品功能或业务流程
- 用户提供用户故事（User Story）或验收标准（AC）
- 用户要求分析某模块的测试范围

## 输出纪律（强制）

- **解析确认只说一次**：`parse_document_from_url` 返回后最多用一句话简述文档内容并立即进入分析动作；后续消息禁止重复"PDF 解析完成"类确认语或文档概述，工具调用之间的过渡消息只说明下一步动作（如"开始 RAG 检索"）。文档内容的详细阐述只出现在正式的需求解析报告中。
- 过渡消息保持简短，不要把报告内容提前拆散到多条过渡消息里。

## 执行流程

### Step 0：初始化全阶段任务清单（强制）

**收到需求后，第一条工具调用必须是 `write_todos`**，创建完整的 5 阶段任务清单（与 SYSTEM_PROMPT 保持一致）。即使当前只进行需求分析，也必须把 Phase 2~5 创建为 `pending` 状态，确保用户在对话一开始就能看到完整的任务全景。

**⚠️ 不要将本 SKILL.md 内部的执行步骤（Step 1/2/3/…）拆解为独立的 todo 项。todo 只包含 Phase 级别的顶层阶段，共 5 项。**

```python

```

|------|---------|------|--------|---------|

| 大型 | >30 | 🏗️ 完整 | 6 阶段 | 在 Phase 2 与 Phase 3 之间增加 Phase 2.5（假设验证） |

>
> ⚡ **快速模式下的 Phase 1 输出要求**：在需求解析报告末尾增加「## 测试策略（精简）」章节，包含：测试类型决策表（简化，无评分矩阵）、测试深度分配、回归策略（1-2 句话）。**不需要**独立的测试策略报告和一次额外的阶段评审。
>
> ⚡ **子任务禁止规则**：`write_todos` 只用于管理 Phase 级别的阶段（phase-1~phase-5），**禁止**将本 SKILL.md 的各步骤（阅读文档、解析内容、建立矩阵、输出报告等）创建为独立的 todo 项。本 Skill 内部步骤在 Markdown 报告中展示进度，不在 todo 面板中重复。

### Step 1：文档结构解析
首先对输入文档进行结构化拆解，识别：
- **文档类型**：PRD / 接口文档 / 用户故事 / 设计稿描述 / 口头需求
- **功能模块列表**：按业务域划分（如：认证模块、订单模块、支付模块）
- **核心业务流程**：主流程 + 分支流程 + 异常流程
- **输入输出定义**：接口参数、UI字段、数据格式
- **业务规则**：约束条件、计算逻辑、状态机规则

### Step 1.5：范围裁剪（强制 — 防止分析范围膨胀）

在进入测试点提取之前，**必须**执行以下裁剪检查：

```markdown
## 范围裁剪规则
1. ✅ **纳入矩阵**：文档中**明确描述了**输入/输出/行为的可验证功能点
2. ❌ **排除到 Out of Scope**：文档仅提及名称但无任何细节的模块/功能（如"任务管理模块"仅出现一次）
3. ❌ **禁止推测性扩展**：不得基于"常见做法"或"行业惯例"自行扩展功能点
4. ❌ **禁止生成空壳条目**：不得为"待补充"/"仅提及"/"无详情"的功能点生成矩阵条目（如 FP-007/FP-008）

## 违反示例（禁止）
| 配气模板 | FP-008 | 配气模板（待补充）| P2 | — | —
→ 没有任何文档数据支撑的功能点条目，必须删除
```

> ⚡ **强制要求**：如果某个模块在文档中只是被提到名字（如"还有任务管理和配气模板两个模块"），但没有任何界面/参数/行为描述，**只能**放入 `Out of Scope` 列表，**不能**生成功能矩阵条目。这一条是硬性规则，违反此规则会导致后续阶段产生大量无效工作。

### Step 2：测试点提取框架（INVEST原则）
对每个功能点，用以下维度提取测试要点：

| 维度 | 提取内容 | 示例 |
|------|---------|------|
| **功能性** | 核心功能是否按预期工作 | 登录成功跳转首页 |
| **数据** | 输入数据的类型、范围、格式 | 手机号11位数字 |
| **规则** | 业务约束和计算逻辑 | 优惠券不可叠加使用 |
| **状态** | 对象状态变化与转换 | 订单从待付款→已付款 |
| **交互** | 组件间联动与依赖关系 | 省市区三级联动 |
| **权限** | 不同角色的访问控制 | 管理员可删除，普通用户不可 |
| **异常** | 错误情况的处理策略 | 网络超时提示重试 |
| **性能** | 响应时间、并发、数据量 | 列表页加载不超过2秒 |

### Step 3：功能矩阵建立
输出标准功能矩阵表格：

```
## 功能测试矩阵

| 模块 | 功能点 | 测试要点 | 优先级 | 风险等级 | 测试类型 |
|------|--------|---------|--------|---------|---------|
| 用户认证 | 手机号登录 | 验证码有效期5min | P0 | 高 | 功能+安全 |
| 用户认证 | 第三方登录 | 微信/支付宝OAuth | P1 | 中 | 功能+兼容 |
```

### Step 3.5：结构化矩阵持久化（强制）

完成功能矩阵表格并**得到用户通过评审后**，**必须调用 `save_feature_matrix_tool`** 将矩阵保存为 JSONL 文件。这确保 Phase 3/4 能读取结构化的功能点清单做覆盖对照，不再依赖对话记忆。

> ⚠️ **重要顺序**：输出 `## 需求解析报告` / `## 功能测试矩阵` 后，**本消息内禁止附带任何工具调用**（包括 `save_feature_matrix_tool`、`write_todos` 等）。系统会基于阶段标题自动弹出人工评审卡片；只有收到用户的通过/跳过决策后，才允许执行保存等后续工具调用。

```python
save_feature_matrix_tool(
    features=[
        {
            "id": "FP-001",
            "module": "用户认证",
            "feature": "手机号登录",
            "test_points": ["验证码有效期5min", "验证码发送频率限制", "错误次数锁定"],
            "priority": "P0",
            "risk_level": "高",
            "test_type": ["功能", "安全"],
            "source": "需求原文 §2.1"
        },
        # ... 每个功能点一条记录
    ],
    # 以下是阶段约束（force — 防止用户反馈在阶段间丢失）
    # 后续 Phase 2/3/4 通过 load_feature_matrix() 读取时也能获取这些约束
    constraints={
        "test_types": ["functional"],          # 用户限定的测试类型
        "scope": "系统配置模块 only",           # 用户限定的范围
        "assumptions_confirmed": False,         # 阻塞性假设是否已逐条确认
        "blocking_assumptions": [               # 阻塞性假设列表
            "配气稳定时间范围 0~9999.99 秒",
            "端口可选范围 COM1~COM10",
            "参数保存后立即生效",
        ],
        "user_feedback_summary": {              # 用户阶段性反馈摘要
            "phase_1": "缩小需求分析报告范围，聚焦测试变更的功能需求",
            "phase_2": "报告整体通过。测试功能类型即可",
            # 后续阶段的反馈在对应阶段完成后追加
        },
    },
    project_identifier=project_identifier,
)
```
> `save_feature_matrix_tool` 同时接收 `features` 和 `constraints` 两个参数。工具将 `features` 写入 JSONL，将 `constraints` 序列化为文件内的一条元数据记录（或独立的 `constraints.json`），确保 Phase 2/3/4 可通过 `load_feature_matrix(project_identifier="...")` 一并获取。

**字段规范**：
- `id`: 功能点唯一编号，格式 `FP-NNN`（如 FP-001, FP-002）
- `module`: 所属业务模块名称
- `feature`: 功能点名称（简短描述）
- `test_points`: 测试要点列表，每项一个具体的测试关注点
- `priority`: P0/P1/P2/P3
- `risk_level`: 高/中/低
- `test_type`: 测试类型列表，只能从以下取值中选择（可多选）：`功能/安全/性能/兼容/接口/UI/数据/异常/边界/单元/集成/端到端/回归/规则/权限/状态`。每个取值单独作为列表元素（如 ["功能", "边界"]），禁止使用 "功能+规则" 这类组合写法
- `source`: 来源标注，如 "需求原文 §2.1" 或 "[RAG·高置信]"

**`constraints` 字段规范**：
- `test_types`: (必填) 用户限定的测试类型列表，如 `["functional"]`
- `scope`: (必填) 用户限定的测试范围，如 `"系统配置模块 only"`
- `assumptions_confirmed`: (必填) 阻塞性假设是否已逐条确认，布尔值
- `blocking_assumptions`: (条件必填) 当 `assumptions_confirmed` 为 `False` 时列出所有阻塞性假设
- `user_feedback_summary`: (建议填写) 各阶段的用户关键反馈，供后续阶段参考

**路径隔离说明**：
- 调用时必须传入 `project_identifier`，工具会自动把 `feature_matrix.jsonl` 保存到该项目的专属目录下
- 例如 `project_identifier="order-system"` 时，实际文件路径为 `order-system/feature_matrix.jsonl`
- 这样可避免不同项目的功能矩阵互相覆盖；Phase 3/4 读取时也应使用同一 `project_identifier` 对应的目录
- 后端读取函数 `load_feature_matrix(project_identifier="...")` 与保存端使用完全相同的路径解析规则，返回的数据中包含 `features` 列表和 `constraints` 对象

> ⚡ **强制要求**：只输出 Markdown 矩阵而不调用本工具的 Phase 1 是不完整的。后续 Phase 3 用例设计和 Phase 4 质量评审将失去确定性覆盖对照的能力。
> ⚡ **顺序红线**：不要在输出阶段报告的同一条消息里调用工具，否则会导致人工评审卡片无法弹出。
重点标注以下高风险区域：
- 🔴 **安全风险**：认证、授权、数据加密、SQL注入点、XSS
- 🟠 **数据完整性风险**：事务处理、并发写入、数据一致性
- 🟡 **兼容性风险**：多端适配、浏览器差异、API版本兼容
- 🔵 **性能风险**：高频接口、大数据量操作、文件上传
- ⚪ **业务逻辑风险**：复杂计算、多条件判断、状态机

生成测试范围说明：

## 测试范围声明

## 输出规范

完成分析后，必须输出以下内容（按顺序）：

> 📌 **TL;DR 摘要（强制 — 放在报告最前面，≤ 5 行）**：
> 在各阶段报告正文前，先输出一个简洁摘要，让评审者 **30 秒内** 抓住关键决策点：
> ```markdown
> ### 📌 报告提要（TL;DR）
> - 功能范围：仅系统配置模块，共 6 个功能点（2个P0 + 4个P1）
> - 本次排除：任务管理和配气模板模块（文档无详情，已归入 Out of Scope）
> - 🚫 阻塞性假设：3 个（取值范围/端口列表/生效策略），需逐条确认
> - 预估用例量：~43 条，全部为功能测试类型
> - 核心风险：端口通信稳定性 + 参数保存失败（P0 级别）
> ```

1. ## 需求解析报告（或 `📊 需求解析报告`）：文档类型、功能模块数量、核心业务流程数
2. ## 功能测试矩阵（或 `📋 功能测试矩阵`）：完整的功能点×测试维度矩阵
3. **⚠️ 风险清单**：按风险等级排序的风险项
4. **📐 测试范围声明**：In/Out Scope 及假设条件
5. **❓ 需澄清问题与默认假设**（有不确定项时必输出，无不确定项可省略）：逐条列出问题 + 分类 + 默认假设 + 影响说明
6. **📈 用例数量预估**：各模块预计测试用例数及总量

## 信息密度指南（所有阶段通用）

当前对话数据显示：5 阶段共 ~550 行输出，用户实际仅吸收了 ~60 行（11%）。以下规则旨在减少结构性噪音：

### 三级信息分类

| 级别 | 标签 | 含义 | 展示方式 | 占报告比例 |
|------|------|------|---------|-----------|
| **决策点** | 🎯 | 用户**必须读**才能做评审决策的内容 | 始终保持展开，放在 TL;DR 之后的第一屏 | ≤20% |
| **支撑细节** | 📋 | 支持决策的数据/表格/计算 | 默认展示但接受用户跳过。对于小型项目（≤10 FP），可折叠为 `<details>` 块 | ≤50% |
| **结构性噪音** | — | 框架性的、各阶段重复的固定文字 | 省略或缩减为一句话引用 | 0%（禁止出现）|

### 各阶段信息密度要求

| 阶段 | 决策点（≤报告的 20%） | 支撑细节（≤报告的 50%） | 噪音（禁止） |
|------|---------------------|----------------------|------------|
| Phase 1 | TL;DR + 功能点清单 + 阻塞性假设 + 用例预估 | 风险清单、范围声明、非阻塞性假设 | NFR 框架（无 NFR 需求时全跳）、需求质量评分（0-3 分时可一句话带过） |
| Phase 2 | TL;DR + 测试类型最终决策 + 深度分配 | 量化评分矩阵（仅在用户未限定时展示）、环境/Mock 策略 | 自动化策略（如确定为全手工测试）、CI/CD 集成策略（如无 CI 需求） |
| Phase 3 | 用例抽样（P0×1 + 边界×1）+ 覆盖对照表 | 汇总表、其余用例 | 设计方法论框架文本（已在 SKILL.md 中，勿在报告中重复） |
| Phase 4 | 覆盖率 + 问题清单 + 综合评分 | 各维度详细得分、隔离 Agent 审查原始发现 | 评分计算公式、质量等级描述（已在 SKILL.md 中，勿在报告中重复） |
| Phase 5 | 文件路径 + 用例数量确认 | 各格式选项对比（仅在用户犹豫时展示） | 版本控制规范（如为首次交付）、工具字段映射表（仅在导入场景展示） |

### 判断标准

每写完一个阶段的报告，在输出前用以下问题自检：
```
□ 如果用户只看 TL;DR 和前 3 个决策点，是否能做出有效评审决策？
□ 报告中是否有 ≥ 30% 的内容与上一阶段重复？
□ 是否有任何段落可以被替换为 "详见 SKILL.md §X.Y" 而不影响理解？
□ 对于 ≤10 FP 的项目，整个报告是否能在 80 行以内？
```

> ⚠️ **精简版报告规则**：当用户要求"缩小范围"或"聚焦"后重新输出报告时：
> - 用户**逐条确认过**的阻塞性假设不应重复列出（对阻塞性假设，"报告已确认" ≠ "逐条已确认"）
>   判断标准：用户输入中明确提到了该假设的内容才视为"已确认"
> - 已被移除的模块/功能点**不应再次出现**在任何表格中
> - 在 TL;DR 中标注"本次变更：相比上一版移除了 X/Y/Z"

> 🔄 **assumptions_confirmed 状态更新时机**：
> - `False → True`：用户在所有阻塞性假设上逐条回复"确认/按默认值继续/修改为XXX"
> - `False` 保持：用户仅回复"报告已确认"但未逐条确认阻塞性假设
> - 当 `assumptions_confirmed` 从 `False` 更新为 `True` 时，Phase 2 应在 `write_todos` 更新阶段状态的同时，更新 feature_matrix.jsonl 中的 `constraints.assumptions_confirmed` 字段

## 关键提示

> ⚡ **强制要求**：需求分析必须在生成任何测试用例之前完成。分析结果将直接影响测试策略选择和用例设计质量。
>
> 🎯 **深度要求**：不满足于表面功能描述，要挖掘隐含需求（如：登录成功后的安全日志记录）、负向需求（如：密码输入错误5次后锁定）、质量需求（如：响应时间要求）。
>
> 🔍 **疑问处理（强制 - 必须给出默认假设）**：发现需求不明确、自相矛盾或有遗漏时，在分析报告中明确标注「需澄清问题」，并**为每一个问题给出一个可执行的默认假设**。给出默认假设的目的是：让评审者可以**一键确认或逐条修改**，而不是被阻塞在"等待回复"状态。禁止只列问题不给假设。
>
> **问题分级机制（强制 — 区分阻塞性与非阻塞性）**：
>
> 每个澄清问题必须标注分类：
> - 🚫 **阻塞性（Blocking）**：回答直接影响 ≥ 5 条用例的测试数据或预期结果，**必须在 Phase 2 开始前由用户逐条确认**。示例：取值范围、生效策略、端口列表
> - ✅ **非阻塞性（Non-blocking）**：回答仅影响 UI 细节或 ≤ 4 条用例，可按默认假设推进。示例：错误提示样式、连接状态指示灯位置
>
> ```markdown
> **判定标准**：
> - 影响边界值测试数据的 → 阻塞性（如取值范围、精度、单位）
> - 影响状态机路径设计的 → 阻塞性（如连接/断开行为、生效策略）
> - 影响安全/权限测试设计的 → 阻塞性
> - 仅影响 UI 文案/样式/位置 → 非阻塞性
> - 仅影响辅助功能（如日志记录格式）→ 非阻塞性
> ```
>
> **阻塞性问题的确认流程**：
> ```
> 1. 在分析报告中用 🚫 标记阻塞性问题，✅ 标记非阻塞性问题
> 2. 阶段评审时，阻塞性问题必须逐条醒目展示：
>    "⚠️ 以下 N 个阻塞性假设将直接影响约 X 条用例的有效性，
>     在您逐条确认前不建议进入 Phase 2："
> 3. 用户只回复"报告已确认"而未逐条确认阻塞性假设时，
>   → 在进入 Phase 2 前再次提醒："检测到 N 个阻塞性假设尚未逐条确认，
>     这些假设影响 X 条边界值用例。是否按默认值继续？"
> 4. 用户明确回复"按默认值继续"或逐条确认后，方可进入 Phase 2
> ```
>
> ### 🏗️ 大型项目 Phase 2.5 强制门禁（>30 FP）
>
> 对于大型项目，Phase 2.5 **不可跳过**。Phase 2 通过后必须进入 Phase 2.5 列出所有阻塞性假设及默认值，用户确认后更新 `constraints.assumptions_confirmed = True`，然后才能进入 Phase 3。
>
> **默认假设的选取原则**：
> - 最保守优先：取值范围的默认假设宁可偏窄不可偏宽（安全性优先）
> - 行业惯例优先：参考同类上位机软件/HMI 软件的常见做法
> - 需求原文优先：若需求中有任何暗示（如截图中的默认值），以此为据
> - 必须在假设表格中标注"若不成立的潜在影响"，帮助评审者判断修改优先级
>
> **输出格式（必须使用以下表格模板）**：
>
> | 序号 | 分类 | 原澄清问题 | 默认假设 | 影响用例数 | 若不成立的潜在影响 |
> |------|------|-----------|---------|-----------|------------------|
> | 1 | 🚫阻塞 | 配气稳定时间的取值范围？ | 0~9999 秒，支持 2 位小数，必填，非负 | ~6 条 | 若范围/精度不同，边界值用例需重写 |
> | 2 | ✅非阻塞 | ... | ... | ~2 条 | ... |
>
> 完成表格后，追加引导语：
> - 如果有阻塞性问题："**以上 🚫 阻塞性假设请逐条确认，确认后进入 Phase 2；✅ 非阻塞性假设如认可可直接跳过。**"
> - 如果全部为非阻塞性："**以上假设如认可可直接确认，如需调整请逐条说明，我将按确认后的约束生成后续阶段的产物。**"
>
> ### ⚡ 测试类型范围确认（推荐询问）
>

>
> | 序号 | 分类 | 原澄清问题 | 默认假设 | 影响用例数 | 若不成立的潜在影响 |

## 与 RAG 检索结果的衔接规范

本 Skill 的输入包含两类信息：
1. **用户原始需求**（PRD/描述/图片等）
2. **`rag-query` Skill 的检索报告**（历史用例、业务规则、缺陷模式等）

### 检索结果的消纳规则

| 检索结果类型 | 如何纳入需求分析 |
|-------------|----------------|
| 业务规则与约束 | 直接纳入功能矩阵的「测试要点」列，标注来源 `[RAG·高置信]` |
| 历史测试用例 | 用于验证当前需求的功能点是否完整（对比历史覆盖范围） |
| 历史缺陷模式 | 纳入风险清单，标注为「已知高频缺陷区域」 |
| 实体定义 | 统一术语使用，确保分析报告中术语与知识库一致 |
| 关联实体/流程 | 补充隐含需求（如：用户注册需考虑与权限模块的联动） |
| 检索缺口 | 在「测试假设」中明确标注「基于需求原文，未检索到历史参考」 |

### 检索结果与需求冲突的处理

当 RAG 检索到的历史规则与当前需求描述冲突时：
1. 在分析报告中标注「⚠️ 知识库冲突」
2. 列出冲突双方：知识库规则 vs 当前需求描述
3. 优先采信**当前需求描述**（需求是最新权威），但建议用户确认
4. 若需求描述不明确，采信**高置信度的知识库规则**作为假设基础

## 非功能需求分析框架（NFR Analysis）

企业级测试必须覆盖功能性需求（FR）和非功能性需求（NFR）。在解析功能需求的同时，系统性识别以下 NFR 维度：

### 性能需求（Performance）

| 检查项 | 需求描述特征 | 测试关注点 |
|-------|------------|-----------|
| 响应时间 | "X秒内返回" / "不超过Y毫秒" | 接口级基准测试、前端渲染时间 |
| 吞吐量 | "支持X并发" / "每秒Y笔交易" | 负载测试、压力测试 |
| 资源占用 | "内存不超过X" / "CPU占用低于Y%" | 性能监控、资源泄漏检测 |
| 数据量 | "支持X万条数据" / "Y GB存储" | 大数据量场景测试、分页/分库验证 |

> 若需求未明确性能指标，在「测试假设」中标注「性能需求未量化，建议补充 SLA 指标」，并基于行业常见标准设计基线用例。

### 安全需求（Security）

| 安全域 | 检查项 | 需求描述特征 |
|-------|--------|------------|
| 认证 | 身份验证强度、多因素认证、会话管理 | "需要登录"、"支持指纹/人脸" |
| 授权 | 角色权限、数据隔离、越权防护 | "管理员可操作"、"仅查看自己的数据" |
| 输入安全 | SQL注入、XSS、CSRF、文件上传安全 | 任何涉及用户输入的功能 |
| 数据保护 | 加密传输、存储加密、敏感信息脱敏 | "密码加密"、"身份证号脱敏" |
| 审计 | 操作日志、访问记录、可追溯性 | "记录操作日志"、"支持审计查询" |

> 若需求未明确安全要求，默认执行**基础安全测试**（OWASP Top 10 核心项），并在风险清单中标注「安全需求未明确，仅覆盖基础项」。

### 兼容性需求（Compatibility）

| 维度 | 检查项 | 测试策略 |
|------|--------|---------|
| 浏览器 | Chrome/Firefox/Safari/Edge 及版本 | 矩阵覆盖主流版本 |
| 设备 | 手机/平板/PC 分辨率适配 | 响应式布局验证 |
| OS | iOS/Android/Windows/macOS 版本 | 核心功能跨平台验证 |
| 数据兼容 | 历史数据迁移、新旧版本数据互操作 | 数据升级/降级测试 |
| API兼容 | 接口版本兼容、字段废弃策略 | 契约测试、回归验证 |

### 可用性与可靠性需求

| 维度 | 检查项 | 测试关注点 |
|------|--------|-----------|
| 可用性 | 错误提示清晰度、操作反馈即时性、无障碍支持 | 错误场景用户体验 |
| 可靠性 | 容错恢复、故障转移、数据一致性保障 | 异常注入测试、混沌测试 |
| 可维护性 | 日志完整性、监控埋点、告警策略 | 运维场景验证 |

## 需求质量评估（PRD Completeness Check）

对输入的需求文档进行质量评分，识别缺失项：

### 完整性检查清单

```
□ 功能描述：每个功能点有明确的输入、处理逻辑、输出
□ 业务规则：约束条件、计算公式、状态流转规则已定义
□ 异常处理：错误场景、边界条件、异常流程已说明
□ 数据定义：字段类型、长度、取值范围、格式要求已定义
□ 权限定义：不同角色的操作权限已明确
□ 性能要求：响应时间、并发数、数据量等已量化
□ 安全要求：认证、授权、数据保护等已明确
□ 兼容性要求：支持的浏览器、设备、OS版本已列出
□ 接口定义：API 的请求/响应格式、错误码已定义
□ 依赖关系：与其他模块/系统的依赖已说明
```

### 评分标准

| 得分 | 等级 | 说明 |
|------|------|------|
| 10/10 | 优秀 | 需求完整，可直接进入测试设计 |
| 7-9/10 | 良好 | 少量缺失，可在测试设计阶段补充假设 |
| 4-6/10 | 一般 | 明显缺失，需标注「需澄清问题」 |
| 0-3/10 | 差 | 严重不足，建议暂停测试设计，先补充需求 |

## 隐性需求挖掘方法（Implicit Requirements Mining）

企业级需求分析不能只依赖文档上写的内容，必须系统性挖掘隐性需求。

### 负向需求挖掘（Negative Requirements）

对每个功能点，主动思考"什么情况下不应该发生"：

| 功能点 | 正向需求 | 负向需求（隐性） |
|-------|---------|----------------|
| 用户登录 | 正确密码可登录 | 密码错误不应登录；密码错误5次应锁定；锁定期间不应允许登录 |
| 订单提交 | 库存充足可下单 | 库存不足不应下单；未登录不应下单；商品已下架不应下单 |
| 数据删除 | 管理员可删除 | 非管理员不应删除；已关联其他数据的不应直接删除；删除后不应影响历史记录 |

### 质量属性需求挖掘

对每个功能点，检查是否隐含以下质量属性要求：

```
□ 一致性：同一操作在不同入口的结果是否一致
□ 原子性：复合操作是否支持回滚（如：支付失败时订单状态是否回退）
□ 幂等性：重复执行同一操作是否产生副作用（如：重复提交订单）
□ 并发安全：多用户同时操作同一资源时的行为
□ 时序敏感：操作顺序是否影响结果（如：先改密码再登录 vs 先登录再改密码）
□ 数据完整性：操作中断（如网络断开）时数据是否一致
```

### 合规性需求挖掘

根据业务领域，自动检查是否需要满足以下合规要求：

| 行业 | 合规标准 | 测试关注点 |
|------|---------|-----------|
| 金融 | 等保2.0、PCI-DSS、JR/T 0071 | 数据加密、访问控制、审计日志、交易一致性 |
| 医疗 | HIPAA、等保2.0、GB/T 35273 | 患者隐私保护、数据脱敏、操作可追溯 |
| 政务 | 等保2.0、GB/T 25000.51 | 国产化适配、数据主权、安全审计 |
| 电商 | 个人信息保护法、GDPR（如有海外用户） | 用户同意管理、数据删除权、跨境传输 |
| 教育 | 个人信息保护法、未成年人保护 | 年龄验证、家长同意、内容过滤 |

## 需求变更影响分析

当用户提供的不是全新需求而是需求变更时，执行以下影响分析：

### 变更影响矩阵

| 变更类型 | 影响范围 | 测试策略调整 |
|---------|---------|------------|
| 新增功能 | 新增模块 + 关联模块 | 全面设计 + 关联模块回归 |
| 功能修改 | 当前模块 + 上下游模块 | 聚焦变更点 + 端到端场景回归 |
| 规则调整 | 所有依赖该规则的模块 | 决策表全量重检 + 规则相关用例回归 |
| 接口变更 | 所有调用方 | 契约测试 + 集成测试 |
| 性能优化 | 全链路 | 基准测试对比 + 压力测试 |
| 安全加固 | 全系统 | 安全专项测试 + 渗透测试 |

### 变更分析输出模板

```markdown
## 需求变更影响分析

### 变更概述
- 变更内容：[简述]
- 变更类型：[新增/修改/删除/优化]
- 影响模块：[列表]

### 影响分析
| 模块 | 影响程度 | 影响说明 | 测试行动 |
|------|---------|---------|---------|
| [模块A] | 高 | [说明] | [行动] |
| [模块B] | 中 | [说明] | [行动] |

### 回归范围建议
- **必须回归**：P0 用例 + 变更直接影响的模块用例
- **建议回归**：P1 用例 + 上下游关联模块用例
- **可选回归**：P2/P3 用例（基于风险评估）
```
