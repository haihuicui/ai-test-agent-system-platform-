# 测试用例设计方法论 Skill

## 激活场景
- 需要为具体功能点生成测试用例
- 用户要求设计某模块或接口的测试用例
- 评估现有用例是否覆盖足够的设计维度

---

## 六大测试设计技术

### 技术一：等价类划分（Equivalence Partitioning）
**原理**：将输入域划分为若干等价类，每类中任意取一个值进行测试。

```
应用步骤：
1. 识别所有输入字段
2. 对每个字段划分有效等价类 + 无效等价类
3. 从每个等价类中取一个代表性值

示例 - 用户名字段（长度4-20个字符）：
┌─────────────────┬──────────────────┬─────────────────────┐
│ 等价类           │ 类别             │ 代表值               │
├─────────────────┼──────────────────┼─────────────────────┤
│ 长度4-20字符     │ ✅ 有效等价类     │ "testuser"（8位）    │
│ 长度1-3字符      │ ❌ 无效等价类     │ "abc"（3位）         │
│ 长度21+字符      │ ❌ 无效等价类     │ "a"×21（21位）       │
│ 含特殊字符       │ ❌ 无效等价类     │ "user@name"          │
│ 纯数字           │ ⚠️ 待定等价类    │ "12345678"           │
└─────────────────┴──────────────────┴─────────────────────┘
```

### 技术二：边界值分析（Boundary Value Analysis）
**原理**：在等价类边界处取值，错误往往出现在边界。

```
边界值选取规则（对于范围 [min, max]）：
  min-1  |  min  |  min+1  |  中间值  |  max-1  |  max  |  max+1

示例 - 年龄范围（18-65岁）：
┌──────┬─────────────────────────────────────────┐
│ 值   │ 用例说明                                  │
├──────┼─────────────────────────────────────────┤
│  17  │ 下边界-1（期望：拒绝，提示"年龄不符合要求"） │
│  18  │ 下边界（期望：接受）                        │
│  19  │ 下边界+1（期望：接受）                      │
│  41  │ 中间值（期望：接受）                        │
│  64  │ 上边界-1（期望：接受）                      │
│  65  │ 上边界（期望：接受）                        │
│  66  │ 上边界+1（期望：拒绝）                      │
│   0  │ 零值特殊处理（期望：拒绝）                   │
│  -1  │ 负数特殊处理（期望：拒绝）                   │
└──────┴─────────────────────────────────────────┘

字符串边界：空字符串("") / 单字符 / 最大长度 / 最大长度+1 / 超长字符串
数字边界：0 / 负数 / 最大整数 / 小数精度边界
日期边界：年份起止 / 月份28/29/30/31日 / 闰年 / 跨年
```

### 技术三：决策表法（Decision Table）
**原理**：用于多条件组合的业务规则测试，穷举条件组合。

```
示例 - 优惠券使用规则：
条件：
  C1: 订单金额 ≥ 100元
  C2: 用户是会员
  C3: 优惠券未过期

结果：
  A1: 可使用优惠券
  A2: 不可使用优惠券
  A3: 显示满减提示

┌────┬────┬────┬────┬────┬────┬────┬────┬────┐
│    │ 1  │ 2  │ 3  │ 4  │ 5  │ 6  │ 7  │ 8  │
├────┼────┼────┼────┼────┼────┼────┼────┼────┤
│ C1 │ T  │ T  │ T  │ T  │ F  │ F  │ F  │ F  │
│ C2 │ T  │ T  │ F  │ F  │ T  │ T  │ F  │ F  │
│ C3 │ T  │ F  │ T  │ F  │ T  │ F  │ T  │ F  │
├────┼────┼────┼────┼────┼────┼────┼────┼────┤
│ A1 │ ✅ │ ❌ │ ❌ │ ❌ │ ❌ │ ❌ │ ❌ │ ❌ │
│ A2 │    │ ✅ │ ✅ │ ✅ │ ✅ │ ✅ │ ✅ │ ✅ │
└────┴────┴────┴────┴────┴────┴────┴────┴────┘
→ 每列生成一个测试用例（可合并规则相同的列）
```

### 技术四：状态转换法（State Transition）
**原理**：针对对象状态机进行测试，验证状态转换的正确性。

```
应用对象：订单、用户账号、审批流程、工单状态

状态图示例 - 订单状态：
[待付款] --支付成功--> [待发货]
[待付款] --取消订单--> [已取消]
[待付款] --支付超时--> [已关闭]
[待发货] --商家发货--> [待收货]
[待发货] --取消申请--> [退款中]
[待收货] --确认收货--> [已完成]
[待收货] --申请退货--> [退款中]
[退款中] --退款成功--> [已退款]

测试用例设计：
1. 正向流程：待付款→待发货→待收货→已完成
2. 取消流程：待付款→已取消（取消按钮是否消失）
3. 超时流程：待付款→已关闭（超时触发）
4. 退款流程：待收货→退款中→已退款
5. 非法转换：已完成→不可再次申请退款（异常验证）
```

### 技术五：场景法（Scenario Method）
**原理**：模拟真实用户操作路径，串联多步骤的端到端场景。

```
场景构建公式：
  基本流（主成功场景）+ 备选流（分支/异常场景）

示例 - 电商下单场景：

基本流：
  选商品→加入购物车→选地址→选优惠券→提交订单→支付→完成

备选流清单：
  AF1: 商品库存不足（选商品后提示售罄）
  AF2: 地址为空（提交时提示添加地址）
  AF3: 优惠券不满足条件（不可选中灰显）
  AF4: 支付失败（跳转支付失败页，提供重试）
  AF5: 支付超时（订单关闭，返回商品列表）
  AF6: 网络中断（支付中断，订单状态处理）
  AF7: 重复提交（防重复下单校验）

每条备选流 = 1个完整测试用例
```

### 技术六：错误推测法（Error Guessing）
**原理**：基于经验和直觉推测最可能出现错误的场景。

```
高价值错误推测点：

【数据层】
- 空值：null / "" / " "（空白字符串） / undefined
- 特殊字符：' " < > & ; # % @ \ / | * ? 
- 超长输入：超过数据库字段长度限制
- 类型混淆：数字字段传字符串，日期格式错误
- 编码问题：中文、emoji、特殊Unicode字符

【业务层】
- 重复操作：快速双击提交按钮
- 并发操作：同时扣减库存/积分
- 跨会话操作：A用户操作B用户的数据
- 状态不一致：前端显示与后端状态不同步

【系统层】
- 文件上传：超大文件 / 0字节文件 / 可执行文件
- 图片处理：非图片文件改扩展名上传
- 时区问题：跨时区的时间计算
- 精度问题：金额计算的小数精度丢失
```

## 设计技术选择决策流程

面对具体功能点时，按以下流程选择最合适的设计技术：

```
Step 1: 识别功能特征
  ├─ 是否有明确的输入字段/参数？
  │    ├─ 是 → 进入 Step 2
  │    └─ 否 → 进入 Step 3
  └─ 是否有多个条件组合影响同一结果？
       ├─ 是 → 优先决策表法
       └─ 否 → 继续判断

Step 2: 输入特征判断
  ├─ 输入有明确取值范围？
  │    ├─ 是 → 等价类划分 + 边界值分析（组合使用）
  │    └─ 否 → 继续判断
  ├─ 输入是自由文本/无范围限制？
  │    ├─ 是 → 错误推测法（重点：特殊字符、超长、注入攻击）
  │    └─ 否 → 继续判断
  └─ 输入是枚举/下拉选项？
       ├─ 是 → 等价类划分（每个选项一个等价类）
       └─ 否 → 继续判断

Step 3: 业务特征判断
  ├─ 功能涉及对象状态变化？
  │    ├─ 是 → 状态转换法
  │    └─ 否 → 继续判断
  ├─ 功能是多步骤业务流程？
  │    ├─ 是 → 场景法（基本流 + 备选流）
  │    └─ 否 → 继续判断
  ├─ 功能有多个参数需组合验证？（参数 ≥ 3）
  │    ├─ 是 → 正交实验法/Pairwise（降低组合爆炸）
  │    └─ 否 → 继续判断
  └─ 历史有高发缺陷或经验可借鉴？
       ├─ 是 → 错误推测法
       └─ 否 → 基础功能验证用例
```

## 组合测试与 Pairwise 方法

当功能点涉及**3个及以上参数**且每个参数有**多个取值**时，全组合测试会产生爆炸性用例数。此时使用 Pairwise（两两组合）方法在覆盖率和效率间取得平衡。

### 适用场景

| 场景 | 示例 | 全组合数 | Pairwise数 |
|------|------|---------|-----------|
| 多字段表单 | 5个字段，每字段4个取值 | 1024 | ~20 |
| 接口参数 | 6个参数，每参数3个取值 | 729 | ~15 |
| 配置项验证 | 8个开关，每个开/关 | 256 | ~12 |

### Pairwise 设计原则

```
目标：确保任意两个参数的所有取值组合至少被覆盖一次。

示例：注册表单有3个参数
  用户名: [有效, 无效格式, 空]
  密码: [有效, 弱密码, 空]
  手机号: [有效, 无效, 空]

全组合：3×3×3 = 27 条
Pairwise：约 9-12 条（任意两个参数的两两组合均被覆盖）
```

> ⚠️ **重要**：Pairwise 不适用于安全测试和关键业务规则验证。对于安全相关参数（如密码强度、权限控制），必须执行全组合测试。

## 接口测试用例设计专项

### 接口测试设计框架

| 测试维度 | 设计要点 | 示例 |
|---------|---------|------|
| **契约验证** | 请求/响应字段名、类型、是否必填 | 字段 `user_id` 应为 `string` 类型且必填 |
| **状态码验证** | 各种场景下的 HTTP 状态码 | 成功→200，参数错误→400，未授权→401，服务端错误→500 |
| **参数边界** | 每个参数的有效/无效/边界值 | `page_size` 有效[1,100]，边界 0/1/100/101 |
| **参数组合** | 多参数同时传值/缺值/错值 | 同时缺失必填参数、部分参数格式错误 |
| **认证鉴权** | Token/Session/OAuth 的有效性 | 无效Token、过期Token、无Token |
| **幂等性** | 重复请求的处理 | 重复提交订单是否只生成一条记录 |
| **并发安全** | 并发调用同一接口 | 同时扣减库存是否超卖 |
| **数据一致性** | 接口操作后的数据状态 | 创建订单后数据库状态、缓存状态是否一致 |

### 接口测试用例模板

```markdown

| **接口路径** | `METHOD /api/v1/xxx` |
| **用例标题** | [接口名] - [测试场景] |
```

4. **降级策略验证**：老旧浏览器不支持新特性时的降级表现

## 设计质量红线

❌ **禁止出现**以下情况（如出现需立即修正）：
- 预期结果使用"正确显示"、"正常运行"、"成功"等无法客观验证的描述
- 一个用例包含多个不相关的验证点（违反原子性：一条用例只验证一个检查点）
- 步骤中使用"等待片刻"、"稍后"等无法量化的时间描述
- 前置条件不可重现（如"用户刚刚进行过某操作"）
- **`test_data` 为空对象 `{}`**
  - 即使纯 UI 操作用例（翻页、导航、按钮点击）没有输入数据，也必须填入至少一个上下文描述字段
  - 正确示例：`{"当前页码": 1, "每页条数": 10}` 或 `{"操作类型": "编辑按钮点击验证"}`
  - ❌ 错误示例：`{}`
- 缺少关键测试数据导致用例无法独立执行
- **接口测试用例缺少具体的请求 Body 和预期响应结构**
- **兼容性测试用例未明确标注目标浏览器/设备版本**
- **测试数据中包含绝对日期/时间戳/环境特定值（系统自动生成值）**
  - 系统自动生成的批次号、文件名、ID等，断言其**格式**而非固定值
  - ❌ `{"任务批次": "20260728001"}` → 非当天执行必失败
  - ✅ `{"任务批次格式": "年月日(8位)+三位顺序号", "期望匹配": "/^\\d{11}$/"}`
  - ❌ `{"默认文件夹名": "BS-20260728143800"}` → 含时间戳
  - ✅ `{"文件夹命名规则": "BS-年月日时分秒, 共14位数字"}`

## Phase 3 矩阵对照（强制）

开始设计用例前，**必须先读取 Phase 1 保存的结构化功能矩阵**，确保不遗漏任何功能点。

### 模块开始前

使用文件读取工具读取功能矩阵。读取路径需与 Phase 1 保存路径保持一致：
- 若 Phase 1 传入了 `project_identifier`，文件位于 `<project_identifier>/feature_matrix.jsonl`
- 若未传入，文件位于 `feature_matrix.jsonl`

**除了功能点清单，还须提取 `constraints` 字段**（如果 Phase 1 已写入），确保用例设计不违背用户限定：
```
从 constraints 中获取：
  - test_types: ["functional"]           → 用例的 case_type 必须在此列表内
  - scope: "系统配置模块 only"            → 仅设计范围内模块的用例
  - blocking_assumptions: [...]          → 边界值使用的范围如来自默认假设，在备注中标注
```

### 🚫 假设确认强制门禁（Phase 3 准入检查）

在开始设计用例之前，**必须**检查 `constraints.assumptions_confirmed` 的值：

```python
constraints = matrix.get("constraints", {})
assumptions_confirmed = constraints.get("assumptions_confirmed", True)  # 无 constraints 时默认为 True

if not assumptions_confirmed:
    blocking = constraints.get("blocking_assumptions", [])
    # ⛔ 阻断进入 Phase 3
    # 输出以下警告并等待用户确认：
    print(f"""
    ⛔ 检测到 {len(blocking)} 个阻塞性假设尚未逐条确认：
    
    {chr(10).join(f'  {i+1}. {a}' for i, a in enumerate(blocking))}
    
    这些假设直接影响约 {estimate_affected_cases(blocking)} 条边界值用例的有效性。
    在确认这些假设前进入用例设计阶段，可能导致大量用例返工。
    
    请选择：
    A. 逐条确认上述假设（推荐）
    B. 回复"按默认值继续" — 接受所有默认假设并继续（风险自负）
    C. 修改某个假设 — 如"配气稳定时间实际范围是 0~60 秒"
    
    ⚠️ 回复 A/B/C 之前，Phase 3 不会开始。
    """)
    # 不执行后续用例设计，等待用户决策
    return  # ← 硬阻断
```

**门禁放行条件**（满足任一即可）：
1. `assumptions_confirmed == True`（Phase 1 或 Phase 2 已更新）
2. 用户回复"按默认值继续"（视为确认所有默认假设）
3. 用户逐条确认/修改了所有阻塞性假设

> ⚡ **目的**：Phase 1 会列出澄清问题，Phase 2 会再次提醒，但这个门禁是**最后的防线**。即使用户在前两阶段都说"报告已确认"但从未逐条确认假设，此门禁仍然会触发。这是为了消除"假设债务静默传播"——整个用例集建立在未经验证的前提上。

> ⚠️ **门禁放行后**：必须在 `write_todos` 中将 Phase 3 状态标记为 `in_progress` 之前，更新 `constraints.assumptions_confirmed` 为 `True`，防止 Phase 4 再次重复检查。

例如当前项目为 `order-system`、当前模块为"用户认证"时：

```
从 order-system/feature_matrix.jsonl 中筛选 module == "用户认证" 的功能点：
  FP-001: 手机号登录 (P0, 高风险)
  FP-002: 第三方登录 (P1, 中风险)
  FP-003: 密码找回 (P1, 中风险)
  ...
```

> 后端代码中可通过 `load_feature_matrix(project_identifier="...")` 获取同一位置的矩阵；
> LLM 直接使用文件读取工具时，请按上述规则拼写路径。

### 模块完成后（逐 test_point 对照 — 强制）

**禁止只做 FP-ID 级计数**。必须展开功能矩阵中每个功能点的 `test_points` 数组，逐项确认覆盖：

1. 从 feature_matrix.jsonl 中读取当前模块每个功能点的 `test_points` 列表
2. 对每个 test_point，确认是否至少有一条用例覆盖（从用例的 `test_case_steps` 和 `expected_result` 中寻找对应该 test_point 的验证逻辑）
3. 在 `write_todos` 中标注覆盖状态（如 "FP-012: 3/3 test_points ✅"）
4. **存在未覆盖的 test_point 时，必须先补用例再标记本模块完成**

**示例**：
```
FP-028（数据隔离规则）的 test_points：
  ✅ 检测报告按实验室隔离 → TC-PR2-TK-008
  ✅ 受试者信息按实验室隔离 → TC-PR2-TK-008
  ❌ 质控任务按实验室隔离 → 未覆盖 → 必须先补用例
```

> ⚡ **目的**：防止"功能点已覆盖但核心测试点漏掉"的盲区。FP-ID 级覆盖率 100% ≠ test_point 级覆盖率 100%。若 feature_matrix.jsonl 不存在，在 `write_todos` 中标注 "[无结构化矩阵，覆盖度可能不完整]"。

### 用例编号规则（强制）

**唯一合法格式**：`TC-[项目]-[模块]-[序号]`（如 `TC-PR2-POS-001`），质量门禁强制校验，无例外。

**编号作用域：当前会话**。每个模块从 001 开始顺序编号，无需关心：
- 历史会话遗留文件中的编号（工作区文件跨会话累积是常态）
- 系统库中已保存的编号

与历史编号重复**不是错误**：统一入库（Phase 4 通过后）时工具按 case_number 去重，
模块自检也只校验当前批次内部的唯一性。

❌ **禁止以下行为**（均会引发编号迁移螺旋，浪费大量轮次）：
- 改用其他编号格式（如 `{模块缩写}-{FP_ID}-{序号}`）——会被质量门禁直接打回
- 为规避与历史文件重复而发明特殊编号段（如从 101/201 开始）
- 为绕过自检将文件重命名为 v2/v3（造成文件碎片）

**同一会话内追加用例**：向本模块当前 JSONL 文件追加时，从该文件现有最大序号 +1 继续；
整体重写模块文件用 `save_test_cases_file`（覆盖写，历史同名文件直接替换）。

**自检失败后的修复流程**：
1. 按返回的 violations 定位具体问题用例与字段
2. 定点修复（少量改动用 edit_file；整体重写用 `save_test_cases_file` 一次完成）
3. 重新调用 `module_self_check_tool`

## Phase 3 完成门禁

**覆盖率必须 100%**：所有功能点至少有一条用例。Phase 3 完成报告中的覆盖对照表会被中间件检测 — 包含 `0% ❌` 或 `无用例` 标记时将自动退回。

### 大型项目（>30 FP）分模块 TodoWrite

Phase 3 开始时将 TodoWrite 拆分为模块级，每个模块一条 todo，逐个推进。全部模块 `completed` 后才能标记 Phase 3 `completed`。中型项目在 activeForm 中标注进度（如 "已完成 2/5 模块"）。

## Phase 3 完成报告可审性要求

当所有模块用例设计完成、准备输出 `## 测试用例生成完成` 触发人工评审时，报告正文**必须**包含具体用例内容，而不仅仅是汇总表。**仅输出汇总表会被系统自动退回，无法进入人工评审卡片**。

### 必须展示的内容

1. **汇总表**：模块、文件、用例数、P0/P1/P2-P3 分布
2. **关键用例抽样展示**：每个模块至少展示 1 条 P0 用例和 1 条边界/异常/安全用例的完整字段：
   - 用例名称、case_number、module、priority、case_type
   - 测试数据 test_data（关键字段）
   - 前置条件 preconditions
   - 测试步骤 test_case_steps
   - **预期结果 expected_result（必须独立展示，不要混在步骤里；可从步骤的 result 字段聚合，也可单独给出）**
3. **设计亮点与风险说明**：
   - 覆盖的边界场景、异常场景、安全场景
   - 未覆盖或需要人工确认的点

### JSONL 文件场景

如果用例已分批写入 JSONL 文件（例如 API 不可用或用例数量过多），**必须**调用 `preview_test_cases` 工具读取文件中的关键用例，并在报告中展示。该工具返回的字段中已包含 `expected_result`，请一并展示。

```python
preview_test_cases(source="/test_cases.jsonl", limit=3)
```

### 禁止行为

- 仅输出"共 XX 条用例，已保存到文件"就进入评审
- 用"质量校验已通过"代替具体用例展示
- 只展示用例标题列表而不展示步骤、数据、预期结果
- 只展示 test_case_steps 而不独立展示 expected_result
- 连续多次被系统退回仍不补充具体用例

> 只有审核者能看到具体用例内容时，Phase 3 评审才有意义。系统会检测报告中是否包含用例编号 + 测试步骤/测试数据，缺少任一要素都会自动退回。
